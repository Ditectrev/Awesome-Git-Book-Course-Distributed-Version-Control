## Introduction to Git

[Git](https://git-scm.com/) is how you record project history, work in parallel, and review changes without overwriting each other. This chapter defines the job, names the problem version control solves, separates [Git](https://git-scm.com/) from [GitHub](https://github.com/) and other hosts, and shows how we practice in the browser so you do not need [Git](https://git-scm.com/) installed on your machine.

### What is [Git](https://git-scm.com/)?

**[Git](https://git-scm.com/)** is a distributed version control system (DVCS). A version control system tracks changes to files over time so you can answer four working questions: what changed, who changed it, when, and—if the commit message is useful—why. Distributed means a complete copy of a repository can hold the full history, not only a copy that lives on one central server. We will unpack that design in Core Principles of Git. For this chapter, treat [Git](https://git-scm.com/) as the engine that stores snapshots of a project.

The official home is [git-scm.com](https://git-scm.com/). The [Git project](https://git-scm.com/about) describes [Git](https://git-scm.com/) as fast, widely used, and released as free and open source software. The [Git documentation](https://git-scm.com/doc) is the canonical reference for the tool itself. [GitHub Docs: About Git](https://docs.github.com/en/get-started/using-git/about-git) is how the same engine shows up when you work on a host.

**[Git](https://git-scm.com/) is software, not a website.** You can run it from a command line, from a desktop app, or through a host's web UI. This book uses the web UI first. The same snapshots, commits, and branches are [Git](https://git-scm.com/) objects either way. The buttons you click on [GitHub](https://github.com/) still create [Git](https://git-scm.com/) history.

A few words we will keep using:

- **Repository (repo):** the project plus its history. On [GitHub](https://github.com/), a repository is the page you open. Under the hood it is a [Git](https://git-scm.com/) database of snapshots.
- **Commit:** a saved snapshot with a message, an author, and a parent (or parents). You will make your first commit in the [GitHub](https://github.com/) web editor in Repositories, Files, and Commits.
- **Branch:** a movable name for a line of work. Branches and Merging is the chapter that makes this concrete.
- **Host:** a service that stores [Git](https://git-scm.com/) repositories and adds a web UI, permissions, and review. Our host is [GitHub](https://github.com/).

**What [Git](https://git-scm.com/) is not:**

- Not [GitHub](https://github.com/). [GitHub](https://github.com/) hosts [Git](https://git-scm.com/) repositories and adds collaboration on top. You can use [Git](https://git-scm.com/) without [GitHub](https://github.com/). You cannot use [GitHub](https://github.com/) as version control without [Git](https://git-scm.com/) running for you.
- Not a backup product by itself. History helps you recover old versions of tracked files. It does not replace a backup of secrets, untracked files, or the host account.
- Not a deploy button. Some hosts wire [Git](https://git-scm.com/) to CI and hosting. This book stays on version control and collaboration. Host CI as a merge gate is Appendix F, not the main path.

[Git](https://git-scm.com/) started as the tool that tracks the [Linux kernel](https://www.kernel.org/). That origin story belongs in History and Evolution of Git. You do not need that history to start clicking in the browser. You do need the distinction we make next: version control is the job, [Git](https://git-scm.com/) is the tool we use for it, and [GitHub](https://github.com/) is where we practice.

### What Problem Version Control Solves

Without version control, a project is a folder that only the latest save can describe. People copy files, email attachments, and rename drafts until nobody can answer "which copy is true?" Version control replaces that mess with a shared history you can inspect, branch, and review.

**The daily problems version control is for:**

1. **Overwriting**
   - Two people edit the same file. The last save wins. The other person's work disappears.
   - Version control records both lines of work so you can combine them, or at least see the conflict instead of silently losing a save.
2. **No latest copy**
   - Folders named `final`, `final-v2`, and `final-FINAL` are not history. They are guesses.
   - A repository has a default branch that points at the current agreed snapshot, plus older commits you can still open.
3. **No audit trail**
   - When something breaks, you need who changed it, when, and in which commit.
   - [Git](https://git-scm.com/) stores that on every commit. On [GitHub](https://github.com/) you will read it on the Commits page, not in a spreadsheet of filenames.
4. **Fear of changing things**
   - If the only copy is the live file, every edit feels risky.
   - Commits let you take a snapshot before you try something. Branches let you try it without touching the default branch. Revert on [GitHub](https://github.com/) (Conflicts and History Repair in the Browser) is how you undo a published commit without pretending it never happened.
5. **Review is guesswork**
   - Asking a teammate to "look at the folder" does not scale.
   - A pull request on [GitHub](https://github.com/) is a review of a [Git](https://git-scm.com/) diff: the exact commits you want to merge, with comments on the lines that changed.

**What you get once history exists:**

- **Snapshots, not a pile of copies.** [Git](https://git-scm.com/) records the state of tracked files at each commit. Core Principles of Git explains why those snapshots are not "a list of diffs" even though [GitHub](https://github.com/) shows you a diff view.
- **Parallel work.** Branches isolate a feature, a fix, or an experiment. You merge when the work is ready. That is the normal [GitHub](https://github.com/) flow we will click through later.
- **Attribution.** Commits carry an author. Review comments on [GitHub](https://github.com/) sit on those commits.
- **Recovery with a record.** You can go back to an older snapshot. You can also see the commits you are leaving behind, which a restored zip file never shows.

Version control is the job. [Git](https://git-scm.com/) is one tool that does that job. Older centralized systems such as [Apache Subversion](https://subversion.apache.org/) and other distributed tools such as [Mercurial](https://www.mercurial-scm.org/) solved overlapping problems with different designs. We are not running those tools. History and Evolution of Git is where we place [Git](https://git-scm.com/) on that timeline. The working rule for this book: if you need history, review, and parallel work, you need a version control system. We teach that system as [Git](https://git-scm.com/), practiced on [GitHub](https://github.com/).

A shared drive, a chat attachment, or a "please use this file" email is not version control. Those channels move bytes. They do not give you a graph of commits you can branch, review, and revert.

### [Git](https://git-scm.com/) vs [GitHub](https://github.com/) vs Other Hosts

Three layers show up in every later chapter. Mixing them up is the most common beginner trap, so we separate them now.

**1. [Git](https://git-scm.com/) — the version control system**

- Stores repositories, commits, branches, and tags.
- Official site: [git-scm.com](https://git-scm.com/). Docs: [Git documentation](https://git-scm.com/doc).
- Does not require [GitHub](https://github.com/). A repository on a USB drive, a company server, or another host is still [Git](https://git-scm.com/) if it uses that format.

**2. A [Git](https://git-scm.com/) host — the service that stores repositories and adds a web UI**

- **[GitHub](https://github.com/)** is our host. It stores [Git](https://git-scm.com/) repositories and adds issues, pull requests, permissions, and the pages we will click. Product: [github.com](https://github.com/). Docs: [GitHub Docs](https://docs.github.com/). Free accounts are enough for the main path; plans are on [GitHub Pricing](https://github.com/pricing).
- The host runs [Git](https://git-scm.com/) for you when you edit in the browser. You still produce [Git](https://git-scm.com/) commits. You are not using [GitHub](https://github.com/) instead of [Git](https://git-scm.com/). You are using [Git](https://git-scm.com/) through [GitHub](https://github.com/).

**3. Collaboration features on top of [Git](https://git-scm.com/)**

- Pull requests, reviews, checks, and branch rules are host features. They describe [Git](https://git-scm.com/) history; they are not extra [Git](https://git-scm.com/) object types.
- [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow) is the usual loop we will practice: branch, commit, open a pull request, review, merge. That loop is a [GitHub](https://github.com/) workflow over [Git](https://git-scm.com/) branches.

**Other hosts (mention only — not a lab):**

The same [Git](https://git-scm.com/) repositories can live on more than one product. These four show up often at work. They speak [Git](https://git-scm.com/). Their web UIs look similar to [GitHub](https://github.com/) (repositories, merge requests or pull requests, permissions). We name them so you can recognize them. We do not open a second classroom on them.

- **[GitLab](https://gitlab.com/)** — [gitlab.com](https://gitlab.com/) (self-managed [GitLab](https://about.gitlab.com/) exists too). Merge requests are the review object that maps to [GitHub](https://github.com/) pull requests.
- **[Bitbucket](https://bitbucket.org/)** — [bitbucket.org](https://bitbucket.org/). Pull requests over [Git](https://git-scm.com/) repositories.
- **[Codeberg](https://codeberg.org/)** — [codeberg.org](https://codeberg.org/). A public [Git](https://git-scm.com/) host with a forge-style web UI.
- **[Azure Repos](https://azure.microsoft.com/en-us/products/devops/repos)** — [Azure Repos](https://azure.microsoft.com/en-us/products/devops/repos) in [Azure DevOps](https://azure.microsoft.com/en-us/products/devops). [Git](https://git-scm.com/) repos plus a web editor and pull requests.

Collaboration, Access, and Other Git Hosts repeats this as a one-line tour. Additional Resources and Reading Materials has Other Git Hosts for pointers. Neither place is a second lab. If your job uses [GitLab](https://gitlab.com/) or [Bitbucket](https://bitbucket.org/), the [Git](https://git-scm.com/) model you learn here still applies. The button labels will differ. The commits will not.

**Working rule:** when we say [Git](https://git-scm.com/), we mean the version control system. When we say [GitHub](https://github.com/), we mean the host where you click. When we say another host, we mean "same [Git](https://git-scm.com/), similar web UI, not our lab."

## History and Evolution of Git

[Git](https://git-scm.com/) did not start as a website. It started as a tool to keep the [Linux kernel](https://www.kernel.org/) moving when a previous tool went away. This chapter places [Git](https://git-scm.com/) on that timeline: centralized systems before it, why Linus Torvalds wrote it, why distributed was a design choice, and how [GitHub](https://github.com/) turned that engine into the social coding workflow we click today. You do not need to install anything. You do need this history so later chapters do not feel like magic buttons.

Canonical history: [Pro Git: A Short History of Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git). Project overview: [Git about](https://git-scm.com/about). Docs: [Git documentation](https://git-scm.com/doc).

### Before Git: Centralized Version Control

Before [Git](https://git-scm.com/), most teams used a **centralized** version control system. One server held the history. You checked out a working copy, edited files, and sent a commit back to that server. If the server was down, you could still type. You could not record history, branch against the project, or see anyone else's latest commit.

**How the centralized model worked:**

1. **One repository on one server.** That copy was the source of truth.
2. **Working copies were not full history.** You had files, plus enough metadata to talk to the server. You did not carry every commit with you.
3. **The network was part of the workflow.** Update, commit, branch, and tag were server operations. [CVS](https://www.nongnu.org/cvs/) said this outright: the network between client and server must be up to check in or update.
4. **Parallel work was possible but expensive.** Two people could edit at once. Merging and branching were the painful parts, especially on older tools.

**Tools you will still hear named at work (we are not running them):**

**[GNU RCS](https://www.gnu.org/software/rcs/)**

- **Primary function:** file-level revision control. One file, many revisions, stored next to that file.
- **Official site:** [GNU RCS](https://www.gnu.org/software/rcs/).
- Fine for a single document. Not a team project model.

**[CVS](https://www.nongnu.org/cvs/) (Concurrent Versions System)**

- **Primary function:** multi-file projects on a central server, built on the same history format as [GNU RCS](https://www.gnu.org/software/rcs/).
- **Official site:** [nongnu.org/cvs](https://www.nongnu.org/cvs/).
- Unreserved checkouts let more than one person edit the same files. Commits were not reliably atomic across files. Branching was notoriously painful.

**[Apache Subversion](https://subversion.apache.org/)**

- **Primary function:** centralized successor to [CVS](https://www.nongnu.org/cvs/). Atomic commits, versioned directories, cheaper branches than [CVS](https://www.nongnu.org/cvs/).
- **Official site:** [subversion.apache.org](https://subversion.apache.org/). Docs: [Subversion documentation](https://subversion.apache.org/docs/).
- Still centralized: the server is the history. A common team path is "[Subversion](https://subversion.apache.org/) until we moved to [Git](https://git-scm.com/)." That is not the [Linux kernel](https://www.kernel.org/)'s path.

**[Perforce P4](https://www.perforce.com/products/helix-core)**

- **Primary function:** centralized version control still used for large, often binary-heavy trees. People at work may still say [Perforce](https://www.perforce.com/) or [Helix Core](https://www.perforce.com/products/helix-core).
- **Official product:** [Perforce P4](https://www.perforce.com/products/helix-core) (the live product URL still uses the Helix Core path).
- We name it so that product is not a mystery. We do not lab it.

**What centralized got right:**

- A single latest copy everyone could name.
- Permissions on one server.
- A model people understood: check out, edit, check in.

**What it did not get right for a project like the [Linux kernel](https://www.kernel.org/):**

- **Single point of failure.** Server loss or lockout paused the project's history.
- **Offline work was a lie.** You could type. You could not commit.
- **Branching at kernel scale.** Thousands of parallel lines of work. Centralized tools of the early 2000s were not built for that.
- **Trust and access.** Kernel work is geographically distributed. Forcing every commit through one admin-owned server fights that.

From 1991 to 2002, [Linux kernel](https://www.kernel.org/) changes often moved as patches and archive files, not as a shared version-control graph. In 2002 the project adopted [BitKeeper](https://www.bitkeeper.org/), a proprietary distributed SCM. That is the bridge to [Git](https://git-scm.com/). If your job used [Apache Subversion](https://subversion.apache.org/) last decade, you still learned centralized version control. The kernel learned distributed version control on [BitKeeper](https://www.bitkeeper.org/) first.

**Working rule:** centralized version control is one server that owns history. [Git](https://git-scm.com/) is not that. When you later click around [GitHub](https://github.com/), it will *look* like one server. The data model underneath is still a distributed [Git](https://git-scm.com/) repository that the host stores for you.

### Linus Torvalds and the Birth of [Git](https://git-scm.com/)

[Git](https://git-scm.com/) exists because the [Linux kernel](https://www.kernel.org/) needed a version control system that was fast, distributed, and not someone else's license.

In 2002 the kernel began using [BitKeeper](https://www.bitkeeper.org/). [BitKeeper](https://www.bitkeeper.org/) was (and is) a distributed SCM. At the time it was proprietary, with a free-of-charge arrangement for kernel work. Maintainers could exchange history without funneling every patch through one [CVS](https://www.nongnu.org/cvs/) server. [Pro Git: A Short History of Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git) records what happened next: in 2005 the relationship between the kernel community and the company behind [BitKeeper](https://www.bitkeeper.org/) broke down, and the free-of-charge status was revoked.

Linus Torvalds created [Git](https://git-scm.com/) as a replacement, using lessons from [BitKeeper](https://www.bitkeeper.org/) without cloning that product. The [GitHub Blog: Git turns 20](https://github.blog/open-source/git/git-turns-20-a-qa-with-linus-torvalds/) dates the first [Git](https://git-scm.com/) commit to **April 7, 2005**. Within days the tool was recording kernel history. The canonical goals, from [Pro Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git), were:

- **Speed.** The [Linux kernel](https://www.kernel.org/) is a huge tree. Status, commit, and merge had to be fast on a laptop.
- **Simple design.** A small set of objects and refs, not a heavyweight server product.
- **Strong support for non-linear development.** Thousands of parallel branches, not a single trunk everyone locks.
- **Fully distributed.** Every clone can hold the full history.
- **Scale.** Handle a project the size of the [Linux kernel](https://www.kernel.org/) without collapsing on data size.

**What that means for you (without a terminal yet):**

- [Git](https://git-scm.com/) was built for a project that already had many maintainers and many branches. Cheap branches are not a later add-on. They are why the tool exists.
- [Git](https://git-scm.com/) is **open source**. The project is released under the [GNU GPL version 2.0](https://www.gnu.org/licenses/old-licenses/gpl-2.0.html). Home: [git-scm.com](https://git-scm.com/). About: [Git about](https://git-scm.com/about). Docs: [Git documentation](https://git-scm.com/doc). Source is developed in [Git](https://git-scm.com/) itself; a common mirror is [git/git](https://github.com/git/git) on [GitHub](https://github.com/).
- Torvalds started it. Junio Hamano took over as maintainer while the kernel went back to being the kernel. You do not need their biographies. You need the product: a distributed engine, not a website.
- [BitKeeper](https://www.bitkeeper.org/) later became open source under the [Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0). That does not change [Git](https://git-scm.com/)'s origin. We mention [BitKeeper](https://www.bitkeeper.org/) so the 2005 story has a name and a URL. We do not run it.

**What [Git](https://git-scm.com/) was not at birth:**

- Not [GitHub](https://github.com/). [GitHub](https://github.com/) is 2008.
- Not a required central server. You could (and still can) exchange [Git](https://git-scm.com/) history with patches, bundles, or a USB drive.
- Not a social network. Issues, pull requests, and stars are host features we cover next.

The kernel still uses [Git](https://git-scm.com/). Browse it at [git.kernel.org](https://git.kernel.org/). That is the same engine you will click on [GitHub](https://github.com/). Different host, same objects.

### Distributed Version Control as a Design Choice

Distributed is not a marketing word. It is the data model. In a centralized system the server *is* the repository. In [Git](https://git-scm.com/), **a clone is a repository**. It has the commits, the branches, and the tags. A host such as [GitHub](https://github.com/) is a convenient, always-on copy with a web UI—not the only place history can live.

**What "fully distributed" bought the kernel, and what it buys you:**

1. **No single copy of history.** If [GitHub](https://github.com/) is unavailable, another clone can still hold the graph. You still need a place to push when you want a shared default branch. You do not need that place in order for [Git](https://git-scm.com/) to *exist*.
2. **Commit without the network.** On a laptop with local [Git](https://git-scm.com/), you commit offline and push later. In this book the host runs [Git](https://git-scm.com/) for you, so your "network" is the browser tab. The design is the same: history is recorded in the repository, then published.
3. **Cheap branches.** A branch is a name pointing at a commit. Creating one does not copy the project on a central server. Branches and Merging is where we click this. The reason it is cheap is this chapter: non-linear development was a goal in 2005, not a later feature.
4. **Review is a graph operation.** You send commits. The other person merges them. Pull requests on [GitHub](https://github.com/) are a host UI on top of that graph. The graph came first.

**[Mercurial](https://www.mercurial-scm.org/)** is the other distributed system born in the same 2005 window, also as a [BitKeeper](https://www.bitkeeper.org/) alternative.

- **Primary function:** distributed version control with a full local repository, like [Git](https://git-scm.com/).
- **Official site:** [mercurial-scm.org](https://www.mercurial-scm.org/).
- Same job, different tool. We are not running [Mercurial](https://www.mercurial-scm.org/). We name it so a "Mercurial repo" at work is not a second mystery. Many hosts that once offered both later standardized on [Git](https://git-scm.com/)—[Bitbucket](https://bitbucket.org/) is the example in the next section.

Core Principles of Git unpacks the mechanics: snapshots rather than file diffs, the three areas, immutable commits, the directed acyclic graph (DAG), and hashes. For this chapter, keep one picture:

- **Centralized:** the server has the database. You have a working copy.
- **Distributed ([Git](https://git-scm.com/)):** you can have the database. A host is one more copy, with permissions and a UI.

**Working rule:** when we say [Git](https://git-scm.com/) is distributed, we do not mean "there is no [GitHub](https://github.com/)." We mean history is not trapped on one server by design. Our classroom still uses one host so you can learn in the browser. That is a teaching choice, not a change to the data model.

### [GitHub](https://github.com/) and the Social Coding Era

[Git](https://git-scm.com/) shipped in 2005 as a command-line engine. Most people did not fall in love with that engine directly. They fell in love with a website that spoke [Git](https://git-scm.com/).

**[GitHub](https://github.com/)** launched in **2008**. Product: [github.com](https://github.com/). About: [GitHub About](https://github.com/about). Docs: [GitHub Docs](https://docs.github.com/). It stores [Git](https://git-scm.com/) repositories and adds a web UI for the collaboration loop we will practice: files, commits, branches, **pull requests**, reviews, issues, and permissions. [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow) is that loop as a documented workflow: branch, commit, open a pull request, review, merge.

**What "social coding" added on top of [Git](https://git-scm.com/):**

- **A URL for every repository.** Clone, browse, and discuss in a browser. You no longer had to email a patch and hope the maintainer applied it.
- **Fork as a one-click copy.** A fork is a [Git](https://git-scm.com/) repository you own, copied from someone else's. Pull Requests, Forks, and Code Review is the chapter. The idea is older than [GitHub](https://github.com/); the button is the era.
- **Pull requests as the review object.** Host feature, not a [Git](https://git-scm.com/) object type. The commits inside are still [Git](https://git-scm.com/).
- **Issues and discussion next to the graph.** Collaboration, Access, and Other Git Hosts covers how far we use them. They are not version control. They sit on the same page as version control.
- **Public work by default (with private repos as a product).** Open source moved from tarball sites to repositories you can fork. That is why a free [GitHub](https://github.com/) account is enough for our lab. Plans: [GitHub Pricing](https://github.com/pricing).

In **2018**, [Microsoft](https://www.microsoft.com/) announced it would acquire [GitHub](https://github.com/) ([Microsoft to acquire GitHub](https://news.microsoft.com/2018/06/04/microsoft-to-acquire-github-for-7-5-billion/)) and completed the acquisition later that year ([Microsoft completes GitHub acquisition](https://blogs.microsoft.com/blog/2018/10/26/microsoft-completes-github-acquisition/)). [GitHub](https://github.com/) remains the product we click. [Git](https://git-scm.com/) remains independent open-source software. Do not mix the owner of a host with the version control system.

**Other hosts (mention only — not a lab):**

The social-coding pattern is not unique to [GitHub](https://github.com/). Other products store [Git](https://git-scm.com/) repositories and add a similar web UI. We named them in Introduction to Git. We name them again so this era is not "there is only one website":

- **[GitLab](https://gitlab.com/)** — [gitlab.com](https://gitlab.com/) (self-managed [GitLab](https://about.gitlab.com/) exists too). Merge requests map to [GitHub](https://github.com/) pull requests.
- **[Bitbucket](https://bitbucket.org/)** — [bitbucket.org](https://bitbucket.org/). Started with [Mercurial](https://www.mercurial-scm.org/), later added [Git](https://git-scm.com/), then standardized on [Git](https://git-scm.com/) ([Sunsetting Mercurial support in Bitbucket](https://bitbucket.org/blog/sunsetting-mercurial-support-in-bitbucket)).
- **[Codeberg](https://codeberg.org/)** — [codeberg.org](https://codeberg.org/). A public [Git](https://git-scm.com/) host with a forge-style UI.
- **[Azure Repos](https://azure.microsoft.com/en-us/products/devops/repos)** — [Azure Repos](https://azure.microsoft.com/en-us/products/devops/repos) in [Azure DevOps](https://azure.microsoft.com/en-us/products/devops).

Collaboration, Access, and Other Git Hosts repeats this as a one-line tour. Additional Resources and Reading Materials has Other Git Hosts. Neither is a second classroom.

**Why this era is why our book stays in the browser:**

The host runs [Git](https://git-scm.com/) and shows you the graph. The [GitHub](https://github.com/) [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files), [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor), and optional [GitHub Codespaces](https://github.com/features/codespaces) exist because social coding put the repository on a URL. [Learn Git Branching](https://learngitbranching.js.org/) is a sandbox for the graph; it is not a host. You still do not need a local `git` binary for the main path.

**Working rule:** [Git](https://git-scm.com/) is the history engine (2005). [GitHub](https://github.com/) is the host where we practice (2008, and still). Other hosts speak the same [Git](https://git-scm.com/). We do not open them as a lab.

### Summary: History and Evolution of Git

We covered the timeline that produced the buttons you will click. Before [Git](https://git-scm.com/), centralized tools such as [GNU RCS](https://www.gnu.org/software/rcs/), [CVS](https://www.nongnu.org/cvs/), [Apache Subversion](https://subversion.apache.org/), and [Perforce P4](https://www.perforce.com/products/helix-core) kept history on one server. The [Linux kernel](https://www.kernel.org/) used patches, then [BitKeeper](https://www.bitkeeper.org/), then—when that free license went away in 2005—Linus Torvalds wrote [Git](https://git-scm.com/) for speed, cheap branches, and a fully distributed model ([Pro Git: A Short History of Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git)). Distributed means a clone can hold the full history; [Mercurial](https://www.mercurial-scm.org/) is the sibling tool from the same year. [GitHub](https://github.com/) (2008) added the social-coding web UI—pull requests, forks, issues—on top of [Git](https://git-scm.com/). [Microsoft](https://www.microsoft.com/) acquired [GitHub](https://github.com/) in 2018. [GitLab](https://gitlab.com/), [Bitbucket](https://bitbucket.org/), [Codeberg](https://codeberg.org/), and [Azure Repos](https://azure.microsoft.com/en-us/products/devops/repos) are the same [Git](https://git-scm.com/), similar UI, not our lab. Next, we will walk through Core Principles of Git.

## Core Principles of Git

History and Evolution of Git explained *why* [Git](https://git-scm.com/) looks the way it does. This chapter is the mental model you will reuse for every later click: how [Git](https://git-scm.com/) stores data, where a change sits before it is history, why a commit is a name you cannot silently edit, how those names form a graph, and what "distributed" means when the classroom is a browser.

You still do not install a local `git` binary. You still do not create a repository yet. Canonical mechanics: [Pro Git: What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F). Host view: [GitHub Docs: About Git](https://docs.github.com/en/get-started/using-git/about-git). When you want to *see* a graph instead of reading one, bookmark [Learn Git Branching](https://learngitbranching.js.org/) — a sandbox, not this chapter's lab. When you want to *see* a real commit, [GitHub](https://github.com/) already shows one; we open that UI on purpose in Repositories, Files, and Commits.

### Snapshots, Not File Diffs

Most older version control systems think in **deltas**: a base file plus a list of line changes over time. [Pro Git: What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F) names that model in [CVS](https://www.nongnu.org/cvs/), [Apache Subversion](https://subversion.apache.org/), and [Perforce P4](https://www.perforce.com/products/helix-core). [Git](https://git-scm.com/) does not store history that way.

**[Git](https://git-scm.com/) stores snapshots.** Each commit is a picture of the tracked project at that moment: every file that belongs in that version, as it looked then. To stay efficient, unchanged files are not copied again. [Git](https://git-scm.com/) stores a link to the same content it already has (a *blob* — the object that holds file bytes). Changed files get a new blob. The commit points at a *tree* (the directory listing) that names which blob belongs at which path. [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) is the internals write-up; Appendix C is where we go deeper. For this chapter, keep the picture: **a commit is a whole-tree snapshot, not a patch file.**

**Why [GitHub](https://github.com/) still shows a diff:**

- Humans review changes, not entire files. A host *computes* a diff between two snapshots so you can read what moved.
- The [GitHub](https://github.com/) commit page, pull-request Files changed tab, and [comparing commits](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/viewing-and-comparing-commits/comparing-commits) view are that computed view. They are not proof that [Git](https://git-scm.com/) stored a list of diffs. The [Git data model](https://git-scm.com/docs/gitdatamodel) is explicit: [Git](https://git-scm.com/) does not store the diff for a commit; it calculates one when you ask.
- [Differences between commit views](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/viewing-and-comparing-commits/comparing-commits#differences-between-commit-views) on [GitHub](https://github.com/) also matter later: the repository Commits page is the graph; a single file's History can omit commits that did not affect that file.

**What this buys you:**

1. **Every commit is a complete project.** Checking out a commit (later, on a branch) means "this tree," not "replay ten years of patches in order."
2. **Unchanged files are cheap.** Two commits that share a README share one blob. History does not grow a new copy of every file on every save.
3. **Branches are cheap.** A branch is a name for a snapshot (a commit), not a duplicated project on a server. Branches and Merging is the click-through. The reason it is cheap starts here.

**Working rule:** think **snapshots**. Read **diffs**. [Git](https://git-scm.com/) stores the former. [GitHub](https://github.com/) displays the latter so you can review.

### The Three Areas: Working Tree, Staging Area, and Repository

[Pro Git: What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F) calls this "the main thing to remember." Files in [Git](https://git-scm.com/) sit in one of three states — **modified**, **staged**, or **committed** — which map to three areas of a project. The [Git data model](https://git-scm.com/docs/gitdatamodel) names the middle area the **index**. People also say **staging area**. Same thing.

**Working tree**

- **Primary function:** the files you edit. A checkout of one snapshot, unpacked so you can read and change them.
- On [GitHub](https://github.com/) this is the file browser and the [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files). In [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) it is the editor tabs ([Visual Studio Code](https://code.visualstudio.com/) for the Web: [VS Code for the Web](https://code.visualstudio.com/docs/editor/vscode-web)).
- Unsaved editor text is not history. Closing the tab without committing leaves the repository as it was.

**Staging area (index)**

- **Primary function:** the list of paths and blobs that the *next* commit will contain. You choose what belongs in the next snapshot instead of dumping every dirty file into history.
- Technical name: **index**. Docs: [Git data model](https://git-scm.com/docs/gitdatamodel). On a machine with [Git](https://git-scm.com/), `git add` updates it and `git status` compares working tree, index, and last commit. We do not run those commands on the main path.
- **[github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor)** is the browser place you will *see* this split: the Source Control view in [Visual Studio Code](https://code.visualstudio.com/) lists **Changes** vs **Staged Changes** ([VS Code Source Control](https://code.visualstudio.com/docs/sourcecontrol/overview)). That is the index, drawn as two lists.
- The basic [GitHub](https://github.com/) [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files) hides the index: **Commit changes** stages and commits in one step. The three areas still exist. The host just does the middle step for you.

**Repository (Git directory)**

- **Primary function:** the object database — blobs, trees, commits, tags — plus the names (refs) that point at commits. This is what a clone copies. [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) and [Git data model](https://git-scm.com/docs/gitdatamodel).
- On [GitHub](https://github.com/) this is the repository itself: the Commits page, the branches, the tags. [GitHub Docs: About commits](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/about-commits) is how that database looks in the UI.

**The loop (same on a laptop and in the browser):**

1. Edit files in the working tree.
2. Stage the paths that belong in the next snapshot (explicit in [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor); implicit on the [GitHub](https://github.com/) [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files)).
3. Commit. That snapshot is now in the repository.

[Learn Git Branching](https://learngitbranching.js.org/) is a graph sandbox. It is the wrong tool if you want to practice the index; it is the right tool when we need you to *see* commits and branches. We will send you there on purpose in Branches and Merging, not as a hidden lab here.

Uncommitted edits are not history. Discarding them in the [GitHub](https://github.com/) web editor is the browser analog; `git restore`, stash, and clean are Appendix G. Do not look for a stash button on [GitHub](https://github.com/). There is not one.

**Working rule:** three areas, even when [GitHub](https://github.com/) hides the middle one. Working tree = what you are editing. Staging area = what the next commit will contain. Repository = saved snapshots.

### Commits as Immutable History

A **commit** is the snapshot plus metadata. [Git](https://git-scm.com/) writes a commit object that records:

- A pointer to the **tree** (the project snapshot).
- A pointer to the **parent** commit (or parents, for a merge). The first commit has none.
- **Author** and committer (name, email, time).
- A **message** — the "why" you will thank yourself for later.

Canonical object layout: [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [Pro Git: Branches in a Nutshell](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell). Host explanation: [GitHub Docs: About commits](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/about-commits). [Git](https://git-scm.com/) names that object with a hash. The hash *is* the commit. There is no separate "commit number 47" that you can reuse.

**Immutable means we add. We do not edit in place.**

- Changing a file on [GitHub](https://github.com/) and clicking **Commit changes** creates a **new** commit on the branch. The old commit is still in the graph. You did not overwrite it.
- A useful message is part of the object. "Fix typo in the last commit" as a *new* commit is the main-path move. Rewriting the old commit (amend, rebase, force-push) is Appendix A, not the normal workflow. The basic [GitHub](https://github.com/) web editor has no force-push button.
- **Revert** on [GitHub](https://github.com/) (Conflicts and History Repair in the Browser) also adds a commit: a new snapshot that undoes an old one. The mistaken commit stays. That is the point of immutable history: the record remains, and the repair is itself a record.
- [Pro Git: What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F) puts it as "Git generally only adds data." After a snapshot is in the database, losing it on purpose is hard — especially once another copy (the host) has it.

**What a commit is not:**

- Not a [GitHub](https://github.com/) pull request. A pull request is a host review object that *points at* commits.
- Not a backup of untracked files or of secrets you never committed.
- Not a license to rewrite published history because a message was sloppy. Add a follow-up commit on the main path.

**Working rule:** a commit is a named, permanent snapshot. Future work is a new commit. Undo on the main path is a new commit too.

### The Directed Acyclic Graph (DAG)

Commits do not form a single numbered list. They form a **directed acyclic graph (DAG)**.

- **Directed:** each commit points at its parent (or parents). The arrows go *backward* in time: the new commit knows what came before it. Parents do not point forward.
- **Acyclic:** you cannot have a loop. A commit cannot be its own ancestor. [Git](https://git-scm.com/) would not know which snapshot is "later."
- **Graph:** more than one line of work can exist at once. A **branch** is a movable name (a ref) that points at a commit. Two branches can share history, then diverge. A **merge commit** has two or more parents and is how those lines join again.

[Pro Git: Branches in a Nutshell](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell) is the picture with objects. [Pro Git: Git References](https://git-scm.com/book/en/v2/Git-Internals-Git-References) is how names (`main`, `HEAD`) sit on top of the graph. We click branches in Branches and Merging. We need the DAG now so those names are not magic.

**Shapes you will see:**

1. **Root commit** — no parent. New repository, first snapshot.
2. **Ordinary commit** — one parent. The usual save on a branch.
3. **Merge commit** — two or more parents. [GitHub](https://github.com/)'s **Create a merge commit** button produces this. Squash-and-merge and rebase-and-merge produce different shapes; that comparison belongs in Branches and Merging.
4. **Diverged branches** — two names pointing at different tips that share an ancestor. A pull request exists because two tips disagree.

**Where to look (pointers, not a lab):**

**[Learn Git Branching](https://learngitbranching.js.org/)**

- **Primary function:** a visual sandbox. Commands *look like* the [Git](https://git-scm.com/) command line; the commit graph updates on screen.
- **Open:** [learngitbranching.js.org](https://learngitbranching.js.org/). Source: [pcottle/learnGitBranching](https://github.com/pcottle/learnGitBranching).
- **What it is not:** it does not push to [GitHub](https://github.com/) and it does not install [Git](https://git-scm.com/). Use it when you want to *see* parents, branches, and merges. We will assign it as practice in Branches and Merging.

**[GitHub](https://github.com/) Network graph**

- **Primary function:** a timeline of commits across the repository and its forks.
- **Docs:** [Understanding connections between repositories](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories) ([GitHub](https://github.com/) Insights → Network).
- We read it on purpose in Branches and Merging (`Reading the Network Graph`). You do not need it to finish this chapter.

The Commits page on a [GitHub](https://github.com/) repository is the same graph, flattened into a list for one branch. Parent links still sit on each commit.

**Working rule:** history is a graph of snapshots. A branch is a name on that graph, not a copy of the project.

### Hashes, SHAs, and Why Identity Matters

Every [Git](https://git-scm.com/) object — blob, tree, commit, tag — is named by a **hash** of its contents. [Pro Git: What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F) calls this integrity: you cannot change a file or a directory without [Git](https://git-scm.com/) knowing. The [Git data model](https://git-scm.com/docs/gitdatamodel) and the [hash function transition](https://git-scm.com/docs/hash-function-transition) design doc are the canonical references.

**What you will see on [GitHub](https://github.com/):**

- A **SHA** (Secure Hash Algorithm) string on every commit. [GitHub Docs: About commits](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/about-commits) calls this unique ID a SHA or hash.
- **[SHA-1](https://csrc.nist.gov/projects/hash-functions)** is the object format you will meet on the main path: **40** hexadecimal characters (`0-9`, `a-f`). Example shape: `24b9da6552252987aa493b52f8696cd6d3b00373` (from [Pro Git](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)).
- [GitHub](https://github.com/) shortens that in lists (often **7** characters). The short form is a prefix of the full hash. The full hash is the identity. Click the commit to see more of it.
- URLs, pull requests, compare views, and revert all hang off that ID. If two people say "the same commit," they mean the same hash.

**Content-addressed storage:**

- The same bytes produce the same blob hash. Two files with identical content share one object, even if their paths differ.
- Change one byte of a file, and that blob gets a new hash. Change a commit message, an author, a parent, or the tree, and the **commit** gets a new hash. Descendants that pointed at the old commit no longer match. That is why "edit history" rewrites a chain, not a line of text. Appendix A is that topic. The main path adds commits instead.

**[SHA-256](https://csrc.nist.gov/projects/hash-functions) exists. You do not need it for this book.**

- [Git](https://git-scm.com/) is migrating object names from [SHA-1](https://csrc.nist.gov/projects/hash-functions) to a stronger hash. The project chose **[SHA-256](https://csrc.nist.gov/projects/hash-functions)** ([hash function transition](https://git-scm.com/docs/hash-function-transition)). Those IDs are **64** hex characters.
- Algorithms are specified by [NIST hash functions](https://csrc.nist.gov/projects/hash-functions) ([FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)).
- The repositories you will click on [GitHub](https://github.com/) in this course use the [SHA-1](https://csrc.nist.gov/projects/hash-functions) object format. Treat 40-character IDs as the working default. If you ever open a [SHA-256](https://csrc.nist.gov/projects/hash-functions) repository, the model is the same: the hash is still the name.

**Working rule:** the SHA is the name of the object. Identical content, identical name. Change the content, change the name. That is why identity matters for review, revert, and "are we looking at the same commit?"

### What Distributed Means in Daily Work

History and Evolution of Git defined distributed as a design choice: a clone can hold the full history. Here is what that means on a Tuesday, including Tuesdays spent in a browser.

**A repository is a full copy of the graph.** Blobs, trees, commits, and the names that point at them travel together. [GitHub Docs: About Git](https://docs.github.com/en/get-started/using-git/about-git) says the same: repositories are self-contained. [GitHub](https://github.com/) is one such copy with a web UI, permissions, and [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow). It is not a checkout that still needs "the real server" in order for history to exist.

**The daily verbs (same [Git](https://git-scm.com/), different buttons):**

1. **Commit** records a snapshot in *this* repository. On [GitHub](https://github.com/) the [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files) and [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) commit into the host copy. On a laptop, you commit into the disk copy and **push** later. The object is the same kind of object.
2. **Publish** means another copy of the graph now has your commits. Push from a clone. On [GitHub](https://github.com/) you already committed on the host, so publish often looks like "the default branch updated" or "the pull request has new commits."
3. **Fetch / pull** means this copy learns commits that already exist on another copy. **Sync fork** on [GitHub](https://github.com/) is that idea for a fork ([About forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/about-forks)). Pull Requests, Forks, and Code Review is the chapter.
4. **Diverge, then review.** Two copies (or two branches on one copy) can point at different tips. A pull request is how [GitHub](https://github.com/) asks to join those graphs. That is distributed daily work, not a special website feature glued on later.

**Copies you will actually meet in this book:**

- **The [GitHub](https://github.com/) repository** — the shared copy we click. For the main path, this *is* your repository. You do not also clone it to disk.
- **A fork** — another full [Git](https://git-scm.com/) repository you own, copied from someone else's. Still [Git](https://git-scm.com/). Still a complete graph.
- **[github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor)** — an editor talking to that host copy. Not a second history database on your laptop.
- **Optional [GitHub Codespaces](https://github.com/features/codespaces)** — a cloud machine with a real clone and [Git](https://git-scm.com/) installed. Another copy of the graph. Never required.
- **[Learn Git Branching](https://learngitbranching.js.org/)** — a toy graph in the browser. Not a copy of your [GitHub](https://github.com/) repository.

**What the browser does not give you, so we do not pretend:**

- Offline commits on an airplane without [GitHub](https://github.com/). That is the laptop/local-[Git](https://git-scm.com/) story in Additional Resources (Git on Your Own Machine). In this course the host is on the network by definition.
- A hidden second clone on your PC. If you only use [GitHub](https://github.com/) and [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor), the distributed model still holds: the host copy is complete, a fork is complete, a teammate's clone is complete. You are working on one of those copies.

Other hosts — [GitLab](https://gitlab.com/), [Bitbucket](https://bitbucket.org/), [Codeberg](https://codeberg.org/), [Azure Repos](https://azure.microsoft.com/en-us/products/devops/repos) — store the same [Git](https://git-scm.com/) objects and speak the same fetch/push graph. Same engine, similar web UI, not our lab.

**Working rule:** distributed means every complete copy can hold the DAG, not "there is no [GitHub](https://github.com/)." Our classroom uses one host so you can learn in the browser. The objects you create there are still [Git](https://git-scm.com/) commits.

### Summary: Core Principles of Git

We covered the model under the buttons. [Git](https://git-scm.com/) stores **snapshots**, not a list of file diffs; [GitHub](https://github.com/) still *shows* diffs so you can review ([Pro Git: What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)). Work moves through **three areas** — working tree, staging area (index), repository — even when the [GitHub](https://github.com/) [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files) stages and commits in one click; [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) is where you will see Changes vs Staged. **Commits are immutable**: new work is a new snapshot with a parent, an author, and a message; revert adds a commit; rewriting is Appendix A. Those commits form a **DAG** (directed, acyclic). A branch is a name on that graph; [Learn Git Branching](https://learngitbranching.js.org/) and the [GitHub](https://github.com/) [Network graph](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories) are how you *see* it later. **Hashes** are identity: [SHA-1](https://csrc.nist.gov/projects/hash-functions) (40 hex characters) on the [GitHub](https://github.com/) main path, with [SHA-256](https://csrc.nist.gov/projects/hash-functions) documented as the successor ([hash function transition](https://git-scm.com/docs/hash-function-transition)). **Distributed** in daily work means each complete copy holds the graph; we commit on [GitHub](https://github.com/), forks are copies, and other hosts speak the same [Git](https://git-scm.com/). Next, we will walk through The Browser Lab.

### Personal vs Organization Repositories

A repository is owned by **someone**. On [GitHub](https://github.com/) that someone is either your personal account or an **organization**. Docs: [Types of GitHub accounts](https://docs.github.com/en/get-started/learning-about-github/types-of-github-accounts), [About organizations](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/about-organizations), [About repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories).

**Personal account repositories**

- **Primary function:** a [Git](https://git-scm.com/) repository *you* own. Your username is in the URL.
- You are the owner. You can add **collaborators**. Permissions: [Permission levels for a personal account repository](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-user-account-settings/permission-levels-for-a-personal-account-repository).
- This is the owner we use for the rest of the main path.

**Organization repositories**

- **Primary function:** a shared account that owns repositories, teams, and settings. You **cannot sign in** as the organization. You sign in as yourself; actions are attributed to your personal account ([About organizations](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/about-organizations)).
- Roles: owner, member, and more ([Roles in an organization](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/roles-in-an-organization)). Teams group members ([About organization teams](https://docs.github.com/en/organizations/organizing-members-into-teams/about-teams)).
- You can create an organization on [GitHub Free](https://docs.github.com/en/get-started/learning-about-github/githubs-products) ([Creating a new organization from scratch](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/creating-a-new-organization-from-scratch)). **Do not create one for this book.** Collaboration, Access, and Other Git Hosts is where we talk teams and permissions. Paid org plans ([GitHub Team](https://docs.github.com/en/get-started/learning-about-github/githubs-products#github-team), [GitHub Enterprise Cloud](https://docs.github.com/en/get-started/learning-about-github/githubs-products#github-enterprise)) are not required.

**Enterprise accounts** sit above organizations on [GitHub Enterprise Cloud](https://github.com/enterprise). They are how companies manage many orgs. You do not need one. If your day job already put you in an org, that is fine — still do the exercises under your **personal** account so the URL is yours.

**Working rule:** you always sign in as a person. An organization is a container, not a login. Our lab repositories will live on your personal account.

### Public, Private, and Internal Visibility

Visibility is who is allowed to *see* the repository. It is not a [Git](https://git-scm.com/) object type. You will choose it when you create a repository in the next chapter. Learn the three words now so the form is not a surprise. Docs: [About repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories) (About repository visibility), [Setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility).

**Public**

- **Who sees it:** anyone on the internet, signed in or not.
- **Who can push:** people with write access, not "the internet."
- Fine for this course. Fine for open source. Not fine for secrets, private keys, or production `.env` files. Secrets That Must Never Be Committed is later; the rule starts here: **do not put secrets in a repository**, public or private.

**Private**

- **Who sees it:** you, people you explicitly share with, and (for org repos) certain organization members.
- [GitHub Free](https://docs.github.com/en/get-started/learning-about-github/githubs-products) includes **unlimited private repositories** on a personal account, with a limited feature set on those private repos. You do not need to pay to hide a practice repo.
- Private is still on [GitHub](https://github.com/)'s servers. It is access control, not encryption at rest you uniquely hold.

**Internal**

- **Who sees it:** every member of a [GitHub Enterprise Cloud](https://github.com/enterprise) **enterprise**, across that enterprise's organizations. Docs: [About internal repositories](https://docs.github.com/en/enterprise-cloud@latest/repositories/creating-and-managing-repositories/about-repositories#about-internal-repositories).
- **You will not see this option** on a personal [GitHub Free](https://docs.github.com/en/get-started/learning-about-github/githubs-products) account. It exists so we can name the word when a workplace repo is "internal" rather than public or private.
- Not a lab. Not a reason to start an enterprise trial.

When you later change visibility, read [Setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility) first — public ↔ private has side effects on forks and some features. We will not flip visibility for fun.

**Working rule:** public means the internet can read it. Private means only people you allow. Internal is an enterprise-only third option you can ignore on the main path. Next chapter you pick public or private; either works for practice.

### [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor): [VS Code](https://code.visualstudio.com/) in the Browser

[github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) is [Visual Studio Code](https://code.visualstudio.com/) running in the browser against a [GitHub](https://github.com/) repository. Microsoft's name for the editor is [VS Code for the Web](https://code.visualstudio.com/docs/editor/vscode-web). [GitHub](https://github.com/)'s how-to is [Using VS Code for the Web from GitHub](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor). It is **free**. It is **not** [GitHub Codespaces](https://github.com/features/codespaces). There is no cloud VM and **no terminal**.

You must be signed in. You do not install [Git](https://git-scm.com/). You do not need a repository of your own yet: you can open any public repository, fork, or pull request.

**Open it (pick one):**

1. On a [GitHub](https://github.com/) repository or pull request, press `.` (period) for the same tab, or `>` for a new tab.
2. In the address bar, change `github.com` to `github.dev`.
3. When viewing a file, use the edit dropdown and choose [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor).

**Do this now:** open [Ditectrev/Awesome-Git-Book-Course-Distributed-Version-Control](https://github.com/Ditectrev/Awesome-Git-Book-Course-Distributed-Version-Control) (or any public repository) and press `.`. You should see the [VS Code](https://code.visualstudio.com/) file tree, editor, and Activity Bar. Click around. **Do not commit.** You do not own this repository; the next chapter is when you commit to one you create.

**What the editor is doing:**

- It runs in the browser sandbox. It does **not** clone the repository to your disk. Most [Git](https://git-scm.com/) operations go through the **[GitHub Repositories](https://marketplace.visualstudio.com/items?itemName=GitHub.remotehub)** extension ([VS Code: GitHub Repositories](https://code.visualstudio.com/docs/sourcecontrol/github)).
- Uncommitted edits live in **browser local storage** until you commit. Close the tab and they can vanish. Commit regularly once you are on a repository you own ([Using VS Code for the Web from GitHub](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor)).
- **Source Control** (Activity Bar) is the three areas from Core Principles: **Changes** vs **Staged Changes**, then a commit. Docs: [VS Code Source Control](https://code.visualstudio.com/docs/sourcecontrol/overview). On [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) commit is typically **Commit & Push** to the [GitHub](https://github.com/) branch — there is no separate laptop copy.
- You can switch branches without a stash. [GitHub](https://github.com/) has no stash button; stash is Appendix G.

**Related URL, same editor family:** [vscode.dev](https://vscode.dev/) is [VS Code for the Web](https://code.visualstudio.com/docs/editor/vscode-web) without starting from a [github.com](https://github.com/) page. `https://vscode.dev/github/OWNER/REPO` opens the same kind of session. We still say [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) in this book because that is the [GitHub](https://github.com/) shortcut.

**What it cannot do (so we do not pretend):**

- No integrated terminal, no `git` binary, no build/run of an app. That is [GitHub Codespaces](https://github.com/features/codespaces) or Git on Your Own Machine.
- Only **web extensions** install (next subsection).
- The basic [GitHub](https://github.com/) [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files) is still the right tool for a one-file change. Use [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) when you want search, many files, or the Source Control view.

**Working rule:** `.` on a [GitHub](https://github.com/) repo opens [VS Code](https://code.visualstudio.com/) in the browser. Free. No VM. No local [Git](https://git-scm.com/). Commit only to repositories you own — starting in the next chapter.

### [GitHub Codespaces](https://github.com/features/codespaces) as an Optional Cloud Machine

### Creating a Repository on [GitHub](https://github.com/)

A repository on [GitHub](https://github.com/) is a [Git](https://git-scm.com/) repository plus the host UI: files, commits, branches, and the pages around them. Docs: [About repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories), [Creating a new repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository).

**Do this:**

1. While signed in, open [github.com/new](https://github.com/new), or use the **+** menu and choose **New repository**.
2. **Owner:** your personal account. An organization is a shared container (The Browser Lab). This practice repository belongs to you.
3. **Repository name:** `hello-git`. [GitHub](https://github.com/) allows at most 100 characters: ASCII letters, digits, and `.`, `-`, `_`. The URL will be `https://github.com/YOUR-USERNAME/hello-git`.
4. **Description** (optional): `Practice repository for the Git book.`
5. **Visibility:** Public or Private. Both work on [GitHub Free](https://docs.github.com/en/get-started/learning-about-github/githubs-products). Public means anyone can read it. Private means you and people you invite. Either way, the repository is on [GitHub](https://github.com/)'s servers. Do not put passwords, keys, or `.env` files in it. Secrets That Must Never Be Committed is the later rule; it already applies.
6. Select **Add a README file**. Leave the `.gitignore` template, the license, and **Choose a template** unset. The following subsections say what those controls write.
7. Leave [GitHub Marketplace](https://github.com/marketplace) app checkboxes clear. If the form offers a prompt that would populate the repository and open a draft pull request, leave that prompt empty. The commits in this chapter should be ones you wrote.
8. Click **Create repository**.

You land on the **Code** tab. The file list shows `README.md`. A link beside the branch name reports the commit count (1 commit). That commit is the root: no parent, message usually **Initial commit**, default branch usually `main`.

If you cleared **Add a README file**, [GitHub](https://github.com/) shows a Quick setup page whose instructions are terminal commands ([Quickstart for repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/quickstart-for-repositories)). Leave that block alone. Use **Add file** → **Create new file**, name the file `README.md`, write one line, and commit directly to the default branch ([Creating new files](https://docs.github.com/en/repositories/working-with-files/managing-files/creating-new-files)). That file becomes the root commit.

**Working rule:** one personal repository, `hello-git`, README on, template off, no terminal.

#### The README as the First File

A README is the front door of the repository. [GitHub](https://github.com/) renders it under the file list on the **Code** tab when the file sits in the repository root (also in `.github` or `docs`; we use the root). Docs: [About the repository README file](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes). It should say what the project is. For `hello-git`, one honest sentence is enough. Content past 500 KiB is truncated on that page; you will not get close.

Checking **Add a README file** writes one [Git](https://git-scm.com/) snapshot:

1. A **blob** for the bytes of `README.md`.
2. A **tree** that lists that path.
3. A **root commit** — no parent — whose message is typically `Initial commit`. The default branch name points at that commit.

That is the snapshot model from Core Principles of Git, produced by a checkbox. One commit can hold many files. A license and a `.gitignore` selected on the same form would be extra blobs in this same root commit, not extra commits.

Open `README.md`. The address bar contains `/blob/main/README.md` (or your default branch name in place of `main`). The branch name means "whatever the tip is right now." Press `y`. [GitHub](https://github.com/) replaces the branch name with the full commit SHA. That URL is a permalink to this version of the file. Docs: [Getting permanent links to files](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files).

**Do this:** read the rendered README on the **Code** tab, open the file, and press `y`. The SHA in the address bar is the root commit. You do not need to copy it yet.

**Working rule:** the README checkbox is the root snapshot. The rendered page is a view. The commit is the object.

#### License, gitignore, and Template Choices

Three optional controls sit on the create form. Leave them off for `hello-git`. Know what they write so the form is not a surprise.

**License**

A license file (usually `LICENSE`) tells other people what they may do with the work. [GitHub](https://github.com/) detects known licenses and shows the name on the repository. Docs: [Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository). The short guide the picker is built from is [choosealicense.com](https://choosealicense.com/).

You are not required to choose a license. With no license file, default copyright applies: you keep the rights, and other people are not granted permission to reuse the work. A public repository without a license is still public to read. It is not a grant to copy.

For this practice repository, leave the license unset. If you later publish a project you want other people to use, add a license on purpose. The create-form picker is only offered for a new repository. Afterward you add `LICENSE` in the web editor ([Adding a license to a repository](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-a-license-to-a-repository)). Read [choosealicense.com](https://choosealicense.com/) before you pick one. MIT is a common permissive license; it is a choice, not a default we assign.

**`.gitignore`**

A `.gitignore` file lists paths [Git](https://git-scm.com/) should leave out of future snapshots. Docs: [Ignoring files](https://docs.github.com/en/get-started/git-basics/ignoring-files). The menu on the create form is filled from [github/gitignore](https://github.com/github/gitignore): starter lists for a language or a tool.

`hello-git` has no build output. Leave the template unset so the root tree is a single README. Releases, Ignore Files, and Repository Hygiene is where we read patterns and where we say again which secrets must never be committed. Selecting a template now would add a file. It would not teach those rules.

**Template repository**

**Choose a template** copies another repository's files into a new one. Docs: [Creating a repository from a template](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template). The new repository starts with a **single commit**. It does not keep the template's history. A fork is the other shape: a fork copies the parent history. Pull Requests, Forks, and Code Review is that chapter. A template is a starter kit. Branches created from a template have unrelated histories, so you cannot open a pull request from them back into the template the way you can from a fork.

Leave the menu empty. `hello-git` should start as your README.

**Working rule:** README on. License, `.gitignore`, and template off. A license is a legal file you add when you mean it. A gitignore template waits for the later chapter. A template repository is a new root commit, not your history.

### Making Your First Commit in the [GitHub](https://github.com/) Web Editor

The root commit already exists. The next commit is a new snapshot: a new tree, one parent (the root), you as the author, and a message you write.

The [web file editor](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files) folds the three areas into one dialog. You edit the working tree in the text box. **Commit changes** stages that file and writes the commit. You do not see **Changes** versus **Staged Changes** here. [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) is where that split is visible (The Browser Lab). Stay in the simple editor for this chapter so each click is one file and one commit. The commit object itself is documented in [About commits](https://docs.github.com/en/pull-requests/reference/commits).

The dialog asks two things that matter:

1. A **commit message**, plus an optional extended description. The next subsection is how to write it.
2. **Where the commit lands.** **Commit directly to the `main` branch** (the default branch name on a new [GitHub](https://github.com/) repository), or **Create a new branch for this commit and start a pull request**.

[GitHub](https://github.com/)'s file docs prefer a new branch when you are editing the default branch, then a pull request ([Editing files](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files)). That is the right habit on a shared repository, and it is [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow). On `hello-git` you are the only writer, and the next chapter is branches. For every commit in this chapter, choose **Commit directly** to the default branch. The button then reads **Commit changes**. **Propose changes** is the other path: a new branch, or an edit in a repository you do not own (which forks and opens a pull request). We want the new snapshot on the default branch so the Commits page is one line.

The same dialog lists verified email addresses on your account. If email privacy is on, the default is a [GitHub](https://github.com/) `noreply` address. Either is a valid author email. Docs: [Setting your commit email address](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address). [Git](https://git-scm.com/) stores an email on the commit. [GitHub](https://github.com/) is choosing it from your account. You do not configure `git` locally to make that true.

**Working rule:** web editor, one file, commit directly to the default branch. The new-branch option waits until we open pull requests.

#### Adding, Editing, and Deleting Files

Three commits, three shapes of diff. Stay on the default branch. Replace the suggested message each time. The message section explains why; the steps include a subject you can use as written.

**1. Add a file** ([Creating new files](https://docs.github.com/en/repositories/working-with-files/managing-files/creating-new-files))

1. On the **Code** tab, open **Add file** → **Create new file**.
2. File name: `NOTES.md`.
3. Body: `A file I will delete after I can see it in history.`
4. Click **Commit changes...**
5. Message: `Add a practice note`
6. Choose **Commit directly** to the default branch.
7. Click **Commit changes**.

The file list now shows `README.md` and `NOTES.md`. The commit count is 2.

**Upload files** can put several files in one commit ([Adding a file to a repository](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository)). **Create new file** is one path. We use it so the diff is a single new blob. In [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor) you can stage several paths and commit once; that is the index, and it is optional here.

**2. Edit a file** ([Editing files](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files))

1. Open `README.md`.
2. Use the pencil (edit) control. The dropdown also offers [github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor). Stay in the web editor.
3. Add a line: `Created in the browser, without installing Git.`
4. **Preview** shows the rendered Markdown. Then **Commit changes...**
5. Message: `Describe the practice repository`
6. Commit directly to the default branch. Click **Commit changes**.

[GitHub](https://github.com/) will often suggest `Update README.md`. That names the file. It does not say why the snapshot exists. Replace it.

**3. Delete a file** ([Deleting files in a repository](https://docs.github.com/en/repositories/working-with-files/managing-files/deleting-files-in-a-repository))

1. Open `NOTES.md`.
2. Open the file menu and click **Delete file**. Clearing the text box and committing would leave an empty blob. Delete the path.
3. Message: `Remove the practice note`
4. Commit directly to the default branch. Click **Commit changes**.

`NOTES.md` is gone from the tip of the default branch. It is still in history. The parent of this commit still points at a tree that contains that blob. Deleting a path in a new snapshot does not rewrite the old snapshot. That is the immutable history from Core Principles of Git.

If the file had been a password or a key, deleting it on the tip would leave the bytes in older commits. [GitHub](https://github.com/) says the same on the delete docs: sensitive data stays in history until you remove it from history. Secrets That Must Never Be Committed, and Common Challenges and Debugging Tips (`I Committed a Secret`), are that problem. `NOTES.md` is not a secret. We delete it so the diff shows a removal.

You now have four commits on the default branch: `Initial commit`, `Add a practice note`, `Describe the practice repository`, `Remove the practice note`.

**Working rule:** add, edit, delete — three commits on the default branch, after the root. The deleted file remains in an older commit.

#### Commit Messages That Future You Can Use

The message is part of the commit object. The hash covers it. Changing the message later means a new hash, which is history rewriting (Appendix A). Write the message as if you will read the Commits page in a month and need to know which snapshot to open.

[Pro Git](https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project#_commit_guidelines) states the usual guidelines. This is the part that matters in the web dialog.

**Subject (the first box):**

- Imperative mood, as an instruction: `Add a practice note`, `Describe the practice repository`, `Remove the practice note`.
- Say what the snapshot is for. `Update README.md`, `Create NOTES.md`, and `Delete NOTES.md` are the labels [GitHub](https://github.com/) suggests. Replace them.
- One skimmable line. [Pro Git](https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project#_commit_guidelines) aims at about 50 characters. You do not need to count. Stop before the subject becomes a paragraph.

**Extended description (the second box):**

- Optional on these three commits. Use it when the subject cannot hold the reason.
- Say why. The diff already shows which lines moved.
- The second box is the body. You do not type a blank line yourself. [Git](https://git-scm.com/) stores subject and body as the message.

You can ignore, for this chapter, the docs' note about putting several authors in one message. One author is enough: you. Signed commits and the verified badge are Appendix F. A team convention such as prefixing `feat:` or `fix:` can wait until a team asks for it. Your own history is readable without that prefix.

**Working rule:** imperative subject, a body only when you need the reason, and a message you wrote rather than the filename [GitHub](https://github.com/) filled in.

### Reading History Without a Terminal

You have a line of snapshots on the default branch. Each commit except the root has one parent. You will read that line in the browser. There is no `git log` on this path. Another host can show the same [Git](https://git-scm.com/) objects with different labels. These clicks are [GitHub](https://github.com/)'s.

#### The Commits Page

On the **Code** tab, select the commit count. The URL looks like `https://github.com/YOUR-USERNAME/hello-git/commits/main`.

That page is one branch of the DAG, drawn as a list, newest first. Each row shows:

- The subject.
- The author.
- When.
- A short SHA. The short form is a prefix of the full hash from Core Principles of Git. Open the commit to see the rest.

The list is every commit reachable on **this branch**, not "every commit that touched one file." A file's **History** view omits commits that did not change that file. [Comparing commits](https://docs.github.com/en/pull-requests/how-tos/commit-changes/comparing-commits) documents the difference (Differences between commit views). When a file's history looks too short, use the repository Commits page.

The list is also not the network of forks and other branches. The [Network graph](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories) is Branches and Merging.

**Do this:** open the Commits page. `Remove the practice note` is at the top. `Initial commit` is at the bottom. That order is newest first.

**Working rule:** the Commits page is one branch, newest first. It is the graph flattened into a list.

#### Inspecting a Commit Diff

Open `Describe the practice repository`. The URL is `https://github.com/YOUR-USERNAME/hello-git/commit/SHA`. Docs: [About commits](https://docs.github.com/en/pull-requests/reference/commits).

On that page you get the subject, the body if you wrote one, the author, the time, a **1 parent** link, the full SHA, and the files that differ from the parent. For this commit that file is `README.md`. Added lines and removed lines are highlighted. [GitHub](https://github.com/) computed that patch by comparing this commit's tree with its parent's tree. [Git](https://git-scm.com/) stored the trees. [Comparing commits](https://docs.github.com/en/pull-requests/how-tos/commit-changes/comparing-commits) is the host view of that idea. Core Principles of Git is why a diff on screen is not proof that history is a list of patches.

The file list on the commit is the paths that **changed**. A later subsection opens the whole tree, including files this commit left alone.

**Do this:**

1. On the README edit, find the line you added.
2. Open `Remove the practice note`. `NOTES.md` is a deletion.
3. Open `Add a practice note`. `NOTES.md` is an addition.

Same path, two commits, two directions. The deletion commit does not erase the addition commit.

**Working rule:** a commit page is one snapshot compared with its parent. The highlighting is a view. The object is the tree.

#### Blobs, Trees, and Parents as [GitHub](https://github.com/) Shows Them

Three URL shapes are the object model in the address bar.

| What you open | URL shape | [Git](https://git-scm.com/) object |
| --- | --- | --- |
| One file | `/blob/<ref>/<path>` | A blob, reached through a tree |
| A directory, or the repository root | `/tree/<ref>` or `/tree/<ref>/<dir>` | A tree |
| One snapshot | `/commit/<sha>` | A commit |

`<ref>` is a branch name or a commit SHA. `main` moves when you commit again. A SHA does not.

**Parents.** A normal commit page shows **1 parent** and a short SHA. That parent is the previous snapshot. Click it and you are on the older commit, still on the same branch history.

Follow **1 parent** from `Remove the practice note`. You pass `Describe the practice repository`, then `Add a practice note`, and you stop at `Initial commit`. The root commit does not list a parent. There is no older snapshot of `hello-git`.

**The whole tree.** The commit page lists files that changed. The snapshot still contains every tracked path. Open `https://github.com/YOUR-USERNAME/hello-git/tree/SHA` with the SHA of `Add a practice note`. That tree lists `README.md` and `NOTES.md`. Open `NOTES.md` there. The URL contains `/blob/` and the body is the sentence you wrote. The **Code** tab of the branch tip does not list `NOTES.md`. The blob is still in the older tree. Deleting the path in a later commit did not destroy the object.

**Permalink.** On a file viewed through `/blob/main/...`, press `y`. The branch name becomes the SHA of the commit at the tip when you pressed it. Docs: [Getting permanent links to files](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files). Use that URL when you mean this version of the file. A `/blob/main/` link means whatever the branch tip is later.

**Do this:**

1. From `Remove the practice note`, click **1 parent** until the page stops offering a parent. That last page is the root.
2. Open the tree for `Add a practice note` and then open `NOTES.md`. The file is still there.
3. On today's `README.md` from the **Code** tab, press `y`. The SHA matches the tip commit (`Remove the practice note`), not the root.

**Working rule:** `/commit/` names the snapshot, `/tree/` is the directory listing, `/blob/` is one file. Parents walk backward. The root stops the walk.

## Branches and Merging

Repositories, Files, and Commits left you with one line of snapshots on the default branch of `hello-git`. A branch is how [Git](https://git-scm.com/) names a second line without copying the project. A merge is how those lines join. On [GitHub](https://github.com/) the join is a button on a pull request. This chapter creates the branch, reads the three buttons, and looks at the graph they leave behind. Reviewers, comments, drafts, and forks are the next chapter. You still do not install [Git](https://git-scm.com/).

**What you need:** `hello-git` on your personal account, with the commits from the previous chapter.

**What you do:** create a branch, commit on it, see that the default branch did not move, then merge through a pull request. You will press **Create a merge commit**, **Squash and merge**, and **Rebase and merge** once each. You will also draw the same shapes in [Learn Git Branching](https://learngitbranching.js.org/).

Canonical pages: [About branches](https://docs.github.com/en/pull-requests/reference/branches), [Managing branches within your repository](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository), [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github), [Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request), [Pro Git: Branches in a Nutshell](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell).

### What a Branch Is

A **branch** is a movable name for one commit. [Pro Git: Branches in a Nutshell](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell) is the object picture: the name is a pointer, and the commits are the snapshots you already know. Creating a branch does not copy files and does not duplicate history. The new name points at the same commit the old name points at, until somebody makes a new commit.

[GitHub](https://github.com/) says the same thing in product language. A branch is a contained line of work — a feature, a fix, or an experiment — started from an existing branch, usually the default branch ([About branches](https://docs.github.com/en/pull-requests/reference/branches)).

**What moves:**

- A new commit on the branch you are viewing moves **that** name forward to the new snapshot. The other name stays where it was.
- Both names still share every ancestor up to the commit where they split.
- The files you see on the **Code** tab are the tree of whichever name is selected. Switching the name switches the tree. It does not create a commit.

The branch dropdown on `hello-git` is that name. In the last chapter it stayed on the default branch, so every commit moved the same pointer. This chapter adds a second pointer.

**Working rule:** a branch is a label on a commit, not a folder of copies. New work moves the label you committed on.

### The Default Branch

When you created `hello-git` with a README, [GitHub](https://github.com/) made one branch and marked it the **default branch**. Docs: [About branches](https://docs.github.com/en/pull-requests/reference/branches) (About the default branch).

That branch is:

- The tree [GitHub](https://github.com/) shows when someone opens the repository.
- The base branch for a new pull request, unless you pick another.
- The branch a local clone checks out first. You are not cloning. The fact still explains why the default branch is the one other people mean by "the project."
- Named `main` on a new repository. [GitHub](https://github.com/) has used that name for new repositories for years. A repository that still says `master` is a later debugging note (Common Challenges and Debugging Tips). Do not rename `hello-git` in this chapter.

You can change which branch is the default ([Changing the default branch](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/changing-the-default-branch)). Leave it. You also cannot delete the default branch until another branch is the default. We will not do that dance.

**Protected branches** and rulesets can require reviews or block a merge. Docs: [About branches](https://docs.github.com/en/pull-requests/reference/branches) (Working with protected branches). `hello-git` has none. Collaboration, Access, and Other Git Hosts is where those rules belong. If a merge button is greyed out on this practice repository, you turned a rule on; turn it off or use a repository without rules. Do not build branch protection for the exercise.

**Working rule:** the default branch is the name the repository opens on. On `hello-git` that name is `main`. Leave it.

### Creating, Switching, and Deleting Branches on [GitHub](https://github.com/)

Docs: [Managing branches within your repository](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository). You need write access. You have it: you own `hello-git`.

**Create.** On the **Code** tab, open the branch dropdown (in the file tree, or at the top of the file list). The field reads **Find or create a branch...**. Type a name that does not already exist, then click **Create branch**. The other path is **View all branches** → **New branch**, where you also pick the source branch. A new branch always starts from an existing branch. If the dropdown was sitting on `main`, the new name points at the same commit `main` points at.

Use a short name without spaces: `status-line`, `squash-line`, `rebase-line`. A slash (`feature/status`) is legal and groups names in the branch list. You do not need it here.

**Switch.** Choose the other name in the same dropdown. The **Code** tab renders that tip. The URL gains the branch name. No commit happens. Unsaved text in the web editor does not travel with you; commit or discard it before you switch.

**Delete.** **View all branches**, then the delete control next to the name. Read the warning and confirm. You cannot delete the default branch. If the branch is the head of an open pull request, deleting it closes that pull request. Deleting a name does not delete commits that another name can still reach. After a merge, `main` can still see the snapshots; only the extra label is gone. [GitHub](https://github.com/) can delete the head branch for you when you merge ([Managing branches within your repository](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository)).

**Do this:**

1. With `main` selected, create a branch named `scratch`. Open **View all branches** ([Viewing branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/viewing-branches-in-your-repository)). `main` is marked default. `scratch` points at the same commit, so the history did not grow.
2. Delete `scratch`. Confirm. `main` and its commits are still there.
3. Select `main` again. Create `status-line`.
4. On `status-line`, edit `README.md` and add a line at the end: `Branch practice: this line started on status-line.` Commit **directly to `status-line`** (not "create a new branch"). Message: `Note the branch practice line`.
5. Switch the dropdown to `main`. The new line is absent. Switch back to `status-line`. The line is there.

Leave `status-line` in place. The merge section uses it. Do not delete `main`.

**Working rule:** create from the branch you mean to start from, switch to read another tip, delete names you are finished with. The default branch stays.

### When to Branch: Features, Fixes, and Experiments

[About branches](https://docs.github.com/en/pull-requests/reference/branches) lists the usual reasons: build a feature, fix a bug, or try an idea without putting it on the default branch yet.

The previous chapter committed straight to `main` on purpose. You were the only writer, and the lesson was one line of commits. That is a poor habit on a repository other people use. A commit on the default branch is immediately the project people open.

**Use a branch when:**

- The change is a feature you want to look at as one unit (`status-line` is the stand-in).
- The change is a fix you might want to drop.
- The change is an experiment. If you delete the branch before merging, the default branch never contained it. Commits that only that name could reach become hard to find. That is the point of an experiment.

**Stay on the default branch when:**

- You are alone in a practice repository and the edit is the lesson itself, as in the last chapter.
- The repository is a scratch pad with no one else reading `main`.

From here on, a change you would want reviewed goes on a branch. [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow) is that loop: branch, commit, pull request, merge. We open the pull request in this chapter only because that is where the merge buttons are. The review half of the loop is next.

**Working rule:** branch for work you might merge, reject, or show to someone else. The default branch stays the agreed tip until you merge.

### Merge, Squash and Merge, and Rebase and Merge

On [GitHub](https://github.com/) you merge by merging a pull request. There is no separate "merge these two branches" button on the **Code** tab. Docs: [Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request), [Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request), [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github).

A new personal repository allows all three methods. The control at the bottom of the pull request is a dropdown:

- **Create a merge commit** (the default **Merge pull request** action).
- **Squash and merge**.
- **Rebase and merge**.

If one of them is missing, the repository's pull-request settings turned it off. The checkboxes are documented in [Configuring commit merging](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-merging-for-pull-requests), [Configuring commit squashing](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests), and [Configuring commit rebasing](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-rebasing-for-pull-requests). On `hello-git` you should not need Settings.

This pull request is only the door to that dropdown. Leave reviewers empty. On the create button, choose **Create pull request**, not the draft option. A draft cannot be merged. Drafts, reviews, and comments are Pull Requests, Forks, and Code Review.

**Do this (merge commit, on the branch you already have):**

1. On `hello-git`, with `status-line` ahead of `main`, use the **Compare & pull request** banner, or open **Pull requests** → **New pull request**. Base: `main`. Compare: `status-line`.
2. Title: `Add a branch practice line`. Create the pull request. Do not request a review.
3. At the bottom, open the merge dropdown and choose **Create a merge commit**. If the button already says **Merge pull request**, that is this method. Confirm.
4. Accept the default merge message. It records the pull request number and the branch name. That message is doing a job the filename suggestions in the last chapter were not doing.
5. Open the new commit on `main`. It lists **2 parents**. One is the previous tip of `main`. The other is the tip of `status-line` (`Note the branch practice line`).
6. Switch the **Code** tab to `main`. The practice line is there. Delete `status-line` if [GitHub](https://github.com/) offers **Delete branch**. `main` still has both parents' snapshots.

**Do this (the other two buttons).** Switch to `main` before each **Create branch**, so the new name starts from the updated default branch. Add each sentence at the **end** of `README.md` so the lines do not collide. Conflicts are the next chapters' problem; this chapter stays on a clean join.

1. Branch `squash-line`. Add `Squash practice: one commit on the default branch.` Commit directly to `squash-line` with message `Add a squash practice line`. Note that commit's short SHA. Open a pull request into `main`, title `Add a squash practice line`. Choose **Squash and merge**, then confirm. The new tip of `main` has **1 parent**, not 2. Its SHA is not the SHA you noted on `squash-line`. The subject is the pull request title. Delete `squash-line` after you have compared the two SHAs.
2. Branch `rebase-line`. Add `Rebase practice: its own commit, new SHA, no merge commit.` Commit directly to `rebase-line` with message `Add a rebase practice line`. Note that SHA. You now have three different joins on one repository. The subsections say why the graphs differ.

**Working rule:** merging on [GitHub](https://github.com/) is a pull-request button. The dropdown chooses the shape. The branch you wrote on can be deleted afterward; the result lives on the default branch.

#### Fast-Forward vs a Merge Commit

[Pro Git: Basic Branching and Merging](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging) describes a **fast-forward**. If the default branch has not moved since you branched, it is a direct ancestor of the branch tip. A fast-forward slides the default-branch name forward to that existing commit. No new snapshot. One parent chain. The SHA on the default branch becomes the SHA you already created.

[GitHub](https://github.com/)'s **Create a merge commit** does not take that shortcut. The docs say the pull request is merged with the `--no-ff` option ([About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)). You get a new merge commit with **two parents** even when a fast-forward was possible. That is why `status-line` produced a merge commit although you had not committed on `main` in between.

The other two buttons do use a fast-forward, after they manufacture new commits ([Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request)):

- **Squash and merge** builds one new commit whose tree matches the branch tip, then fast-forwards the base branch to it. One parent. New SHA.
- **Rebase and merge** copies each branch commit onto the base branch as a new commit, then fast-forwards. One parent per copied commit. New SHAs. [GitHub](https://github.com/) always updates the committer and always writes new SHAs, including when the copy sits directly on the old tip ([About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)). A pure fast-forward would have reused the SHA. This button does not.

If `main` had gained a commit your branch does not contain, a fast-forward is impossible. A merge commit is the join. A rebase replays your commits on top of that newer tip. Same files edited on both sides produce a conflict. Conflicts and History Repair in the Browser is that editor. We avoided it by adding lines at the end and by branching from current `main`.

**Working rule:** fast-forward means the branch name slides to a commit that already exists. [GitHub](https://github.com/)'s merge button writes a two-parent commit anyway. Squash and rebase fast-forward to commits they just created, so the SHAs are new.

#### When Each [GitHub](https://github.com/) Merge Button Fits

All three land the same tree when the pull request is one clean change. They land different history. Docs: [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github).

**Create a merge commit** when you want the branch preserved as a unit. The two parents say "this tip of `main` and that tip of the branch became this snapshot." The merge message names the pull request. Every commit you made on the branch stays on `main`, including the noisy ones (`wip`, `fix typo`). Use it when that trail is worth keeping. You already did this with `status-line`.

**Squash and merge** when the branch history is scratch work and the default branch should gain one snapshot. [GitHub](https://github.com/) says work-in-progress commits help on the branch and do not all need to stay on the default branch. The cost, which the same page states: you lose when each small commit happened and who authored those squashed commits, as separate objects on the default branch. The new commit's author is you, at merge time. Its subject should be the imperative pull-request title (`Add a squash practice line`), not a list of leftovers. One more cost from that page: if you keep committing on the old branch and open another pull request, commits you already squashed can show up again, because those SHAs were never parents of `main`. Delete the branch after the squash, and start the next idea from fresh `main`.

**Rebase and merge** when each commit on the branch is already a commit you want on the default branch, in a straight line, with no merge bubble. Subjects stay. SHAs change. This is not an interactive rebase: you do not reorder, squash, or edit messages in this button. You do not force-push. The [GitHub](https://github.com/) docs mention force-push for people who must update a branch from the command line before this button will run. That path is Appendix A. The web editor has no force-push button. On `hello-git` the button worked because the branch was a straight line of new commits on top of `main`.

A merge queue, or a ruleset that allows only one method, removes the dropdown. You will not meet a merge queue on this practice repository. The name is enough so the missing dropdown is not a mystery later.

**Working rule:** merge commit keeps the join and the branch commits. Squash keeps one new snapshot. Rebase keeps each commit and replaces the SHAs. Pick the shape you want strangers to read on `main` in a year.

#### Reading the Network Graph

The **Network** graph draws commits across the repository's branches and forks. Docs: [Understanding connections between repositories](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories). Open `https://github.com/YOUR-USERNAME/hello-git/network`, or the repository's **Insights** → **Network**.

**How to read the dots on `hello-git`:**

- Each dot is a commit. Time runs along the graph. Your root commit is the oldest.
- A line is a branch name moving from parent to child.
- The merge commit from `status-line` is a dot with two incoming lines: `main` and the branch. That is the two parents from the commit page, drawn sideways.
- The squash commit and the rebase commit sit on the `main` line with one parent each. They do not draw a second line into `main`, because [GitHub](https://github.com/) fast-forwarded after writing new commits.
- Forks would appear as more lines. You have not forked this repository. Pull Requests, Forks, and Code Review is that copy.

The graph can lag a minute behind a merge. Reload if the new dot is missing. The Commits page on `main` is the same history as a list, newest first, and it updates immediately. Use the list to read messages and SHAs. Use the network graph to see which joins had two parents.

**Do this:** open the network graph. Find the two-parent join. Find the later dots that stay on one line. Click a dot if the graph links it to the commit page, and check the parent count against what you saw earlier.

**Working rule:** two incoming lines mean a merge commit. A single line through a new dot means squash or rebase-and-merge. The Commits page is the same graph as text.

## Pull Requests, Forks, and Code Review

Branches and Merging used a pull request as the door to the merge buttons. This chapter is the pull request itself: a proposal to merge one branch into another, with a place for comments, a draft stage, and a merge box that can wait on checks. When the repository is not yours, the same proposal starts from a fork.

You still do not install [Git](https://git-scm.com/). The practice repository is still `hello-git`.

**What you do:** open one pull request on `hello-git`, comment on the diff, apply a suggestion, and merge it. Open a second and close it without merging. Then fork [octocat/Spoon-Knife](https://github.com/octocat/Spoon-Knife), read the cross-fork form, and sync the fork. You do not send that exercise to the upstream repository.

Canonical pages: [Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests), [Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request), [Pull request reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews), [Forks](https://docs.github.com/en/pull-requests/reference/forks).

### What a Pull Request Is

A **pull request** is a [GitHub](https://github.com/) proposal to merge one branch into another. [GitHub](https://github.com/) calls it the collaboration feature for discussing a change before it lands ([Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)). It is not a [Git](https://git-scm.com/) object. The commits on the branch are the [Git](https://git-scm.com/) objects. The pull request points at two branch names:

- **Base** (or base branch): where you want the result to land. On `hello-git` that is `main`.
- **Compare** (or head): the branch that holds the new commits.

[GitHub](https://github.com/) lays that proposal out in tabs ([Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)):

- **Conversation** — the description, the timeline, comments, and reviews.
- **Commits** — the snapshots on the head branch.
- **Checks** — automated results. `hello-git` has none yet.
- **Files changed** — the diff a reviewer reads. The same computed diff as a commit page, for every commit in the proposal.
- **Findings** — automated code-review results such as code scanning. Empty on this practice repository. Leave it empty.

The **merge box** at the bottom is where the three buttons from Branches and Merging live, and where [GitHub](https://github.com/) reports blockers (a draft, a failing check, a missing review).

**Working rule:** a pull request is a review of commits, not a new kind of snapshot. Base is the destination. Compare is the work.

### Opening a Pull Request from a Branch

A pull request inside one repository needs two different branch names ([Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)). You already opened three of these to reach the merge buttons. This time the pull request stays open long enough to review.

**Do this:**

1. On `hello-git`, select `main`. Create `review-line`.
2. Edit `README.md` and add a line at the end: `Review practice: a line for comments.`
3. Commit directly to `review-line`. Message: `Add a line for review`.
4. Use **Compare & pull request**, or **Pull requests** → **New pull request**. Base: `main`. Compare: `review-line`.
5. Title: `Add a line for review`. Description: one sentence on why the line exists. A description can also name an issue (`Fixes #1` closes that issue when the pull request merges). You have no issue. Skip the keyword.
6. Open the create-button dropdown and choose **Create draft pull request**. The next section is why.

Leave reviewers empty. The form is the same one Branches and Merging used. The draft choice is the new part.

**Working rule:** base `main`, compare your branch, imperative title, draft until you mean to ask for review.

### Reviewers, Comments, and Suggested Changes

A review is a person responding to the diff. Docs: [Pull request reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews), [Commenting on a pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/commenting-on-a-pull-request), [Reviewing proposed changes in a pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request).

**Reviewers.** Requesting a review takes write access. The person you request needs read access, and [GitHub](https://github.com/) notifies them. On `hello-git` you are the only account. The reviewer box stays empty. You also cannot approve your own pull request ([Reviewing proposed changes in a pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)). Adding a collaborator is Collaboration, Access, and Other Git Hosts. Do not create a second account for this chapter.

A submitted review is one of three choices:

- **Comment** — feedback without an approve or a block.
- **Approve** — the reviewer says the change can merge.
- **Request changes** — the reviewer wants another commit before merge.

**Comments.** The **Conversation** tab takes a general note. **Files changed** takes a note on a line or a file. Line comments are where implementation questions belong.

**Suggested changes.** In a line comment, the suggestion control inserts a block [GitHub](https://github.com/) can apply as a commit on the head branch. The author (anyone with write access) clicks **Commit suggestion**, or batches several with **Add suggestion to batch** and then **Commit suggestions**. Docs: [Incorporating feedback in your pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/incorporating-feedback-in-your-pull-request). That commit is an ordinary [Git](https://git-scm.com/) snapshot. The pull request updates because the head branch moved.

**Do this** after the pull request is ready for review (next section). If you are still on the draft, mark it ready first.

1. Open **Files changed**. Comment on the new README line: `Leaving a note on this line.`
2. Start another line comment on that same line. Use the suggestion control so the suggested line is `Review practice: a line for comments and a suggestion.`
3. Submit the comment. Click **Commit suggestion**. Message: `Apply the review suggestion`.
4. Open **Commits**. The head branch now has `Add a line for review` and `Apply the review suggestion`.
5. Open **Review changes** if you want the summary box. **Comment** is the choice you can submit on your own pull request. **Approve** will not count: it is your pull request.

**Working rule:** comments sit on the pull request. A suggestion, once committed, is a new snapshot on the head branch. You cannot approve yourself.

### Draft Pull Requests

A **draft** is a pull request you do not want merged yet. Docs: [Changing the stage of a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-stage-of-a-pull-request), and the draft section of [Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests).

The merge box refuses a draft. **Ready for review** lifts that. You can turn an open pull request back into a draft later; people already notified stay notified. Marking ready can also request review from code owners. `hello-git` has no [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) file. Nothing extra is requested. CODEOWNERS as a required review is Collaboration, Access, and Other Git Hosts.

**Do this:** open the draft you just created. In the merge box, click **Ready for review**. Then do the comments in the previous section. The merge button stays unused until Merging and Closing Pull Requests.

**Working rule:** draft means "not a merge candidate." Ready for review means the diff is fair game for comments and, later, the merge button.

### Checks, Statuses, and Required Reviews

The **Checks** tab and the merge box report automation. Docs: [Status checks](https://docs.github.com/en/pull-requests/reference/status-checks).

[GitHub](https://github.com/) has two kinds:

- **Checks** — detailed results from [GitHub Apps](https://docs.github.com/en/apps), including [GitHub Actions](https://docs.github.com/en/actions).
- **Commit statuses** — a simpler pass or fail posted by an outside service.

`hello-git` has no workflow and no outside service. The tab is empty. That is success for this chapter. An empty tab does not mean the README was tested. It means nobody configured a test. Wiring [GitHub Actions](https://docs.github.com/en/actions) as a merge gate is Appendix F. Do not add a workflow now.

If a branch protection rule or a ruleset marks a check or a review as required, the merge box waits until that requirement passes ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). A skipped [GitHub Actions](https://docs.github.com/en/actions) job reports success and does not block. `hello-git` has no such rule. Do not add one. The merge box on your pull request should offer the same three buttons as the last chapter, once the pull request is ready for review.

**Working rule:** checks are programs the repository owner attached. No check configured means no signal, not a passing grade. Required reviews are a branch rule, not a property of [Git](https://git-scm.com/).

### Merging and Closing Pull Requests

Merging lands the head branch on the base using one of the three methods from Branches and Merging. Docs: [Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request). Closing records that you will not merge it. Docs: [Closing a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/closing-a-pull-request).

**Do this (merge):**

1. On `Add a line for review`, with the pull request ready for review, choose **Create a merge commit** and confirm.
2. Accept the default merge message. Delete `review-line` when [GitHub](https://github.com/) offers it.
3. On `main`, the README contains the suggested line. The merge commit has two parents, as in the last chapter.

You do not need to press **Squash and merge** or **Rebase and merge** again.

**Do this (close without merging):**

1. From `main`, create `close-me`. Add a line at the end of `README.md`: `Close practice: this line should not land.` Commit directly to `close-me`. Message: `Add a line we will not merge`.
2. Open a pull request. Title: `Add a line we will not merge`. This time choose **Create pull request**, not a draft.
3. At the bottom, below the comment box, click **Close pull request**. Leave the branch in place for a moment.
4. Switch the **Code** tab to `main`. The close-practice line is absent. Switch to `close-me`. The line is still on that branch. Closing did not move `main` and did not delete the commits.
5. Delete `close-me` from **View all branches** when you are done looking. A closed pull request can be reopened from its page if the branch still exists. Reopen is optional.

**Working rule:** merge updates the base branch. Close leaves the base branch alone. Deleting the head branch is a separate click either way.

### Fork vs Clone as a Mental Model

Three copies get confused. Only one of them is this chapter's lab.

**A branch** is a name inside one repository. `review-line` and `main` were two names in `hello-git`.

**A fork** is a separate repository on [GitHub](https://github.com/). It starts as a copy of another repository, the **upstream**, and stays linked to it. Docs: [Forks](https://docs.github.com/en/pull-requests/reference/forks). Under the fork's name, [GitHub](https://github.com/) shows which upstream it came from. The fork has its own settings, issues, pull requests, and actions. A branch cannot. You can fork any public repository to your personal account. The fork copies history, which is why you can open a pull request back to upstream. A repository created from a template does not: that was one new root commit, in Repositories, Files, and Commits.

**A clone** is a copy of a [Git](https://git-scm.com/) repository on a machine: your laptop, or a cloud machine such as [GitHub Codespaces](https://github.com/features/codespaces). Docs: [Cloning a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository). Cloning is how Git on Your Own Machine starts. This book still does not ask you to clone. A fork is not a clone. A fork lives on [GitHub](https://github.com/). A clone lives where [Git](https://git-scm.com/) is installed.

**Working rule:** branch = a name in one repo. Fork = another repo on [GitHub](https://github.com/), linked upstream. Clone = a repo on a machine. We fork. We do not clone.

### Contributing to Someone Else's Repository

You cannot push a branch to a repository you do not have write access to. You fork it, commit on the fork, and open a pull request whose base is upstream and whose compare branch is on your fork. Docs: [Fork a repository](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/fork-a-repo), [Creating a pull request from a fork](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork).

[GitHub](https://github.com/)'s own walkthrough uses [octocat/Spoon-Knife](https://github.com/octocat/Spoon-Knife). Use that. Do not open a practice pull request against this book. A real correction still uses these steps, with upstream [Ditectrev/Awesome-Git-Book-Course-Distributed-Version-Control](https://github.com/Ditectrev/Awesome-Git-Book-Course-Distributed-Version-Control). Practice lines do not belong there.

The pencil on a file in someone else's repository is the same path, started for you. [Editing files](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files) forks the repository and leads to **Propose changes**. We will fork first so the two repositories are visible.

**Do this:**

1. Open [octocat/Spoon-Knife](https://github.com/octocat/Spoon-Knife). Click **Fork**.
2. Owner: your personal account. Select **Copy the default branch only**. [GitHub](https://github.com/) recommends that for a contribution. Click **Create fork**.
3. On your fork, the page names the upstream under the repository name. Create `practice-fork` from the default branch. Change one file by a single obvious line. Commit directly to `practice-fork`. Message: `Practice a fork commit`.
4. Start **Compare & pull request**. On the form, click **compare across forks**. Set the base repository to `octocat/Spoon-Knife` and the base branch to its default branch. Set the head repository to your fork and the compare branch to `practice-fork`.
5. Read the title [GitHub](https://github.com/) filled in. Stop. Do not click **Create pull request**. The form is the whole lesson. An open pull request would propose your exercise line to a project you do not maintain.

Your commit remains on your fork. Upstream does not have it.

**Working rule:** no write access, no branch on their repository. Fork, commit, compare across forks. Create the pull request only when the change is one you mean them to merge.

### Syncing a Fork in the [GitHub](https://github.com/) Interface

Upstream will gain commits you do not have. **Sync fork** copies those commits onto a branch of your fork. Docs: [Syncing a fork](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork).

**Do this:**

1. Open your fork of [octocat/Spoon-Knife](https://github.com/octocat/Spoon-Knife). Select the default branch, not `practice-fork`.
2. Above the file list, open **Sync fork**.
3. If [GitHub](https://github.com/) says the branch is up to date, stop. That is a finished sync: you forked recently, and you did not commit on this branch.
4. If it lists upstream commits, read them and click **Update branch**. Those commits land on your default branch. Your `practice-fork` branch is untouched until you merge or rebase it yourself.

When upstream commits and your branch edited the same lines, [GitHub](https://github.com/) asks for a pull request to resolve conflicts. That editor is Conflicts and History Repair in the Browser. Do not hunt for a conflict on Spoon-Knife. The up-to-date message is the result we want.

Sync is not a pull from your laptop. It is the host copy of your fork learning commits that already exist on upstream. Core Principles of Git called that fetch. The button is the browser form of it.

**Working rule:** sync the fork's default branch from upstream. Up to date is a successful result. Conflict resolution waits for the next chapter.

### Summary: Pull Requests, Forks, and Code Review

We treated the pull request as the review, not only as a merge button. A pull request is a [GitHub](https://github.com/) proposal to merge a compare branch into a base branch; the commits are still [Git](https://git-scm.com/) ([Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)). You opened `review-line` as a draft ([Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request), [Changing the stage of a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-stage-of-a-pull-request)), marked it ready, commented on the diff, and committed a suggestion onto the head branch ([Incorporating feedback in your pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/incorporating-feedback-in-your-pull-request)). You cannot approve your own pull request. The Checks tab was empty because no [GitHub Actions](https://docs.github.com/en/actions) workflow is configured ([Status checks](https://docs.github.com/en/pull-requests/reference/status-checks)). Merging updated `main`. Closing `close-me` did not ([Closing a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/closing-a-pull-request)). A fork is another [GitHub](https://github.com/) repository linked to upstream; a clone is a copy on a machine; a branch is neither ([Forks](https://docs.github.com/en/pull-requests/reference/forks)). You forked [octocat/Spoon-Knife](https://github.com/octocat/Spoon-Knife), read **compare across forks**, and did not create the upstream pull request. **Sync fork** on the default branch is how that fork learns new upstream commits ([Syncing a fork](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork)).
